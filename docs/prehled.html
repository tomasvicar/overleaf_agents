overleaf_agents

Předbuilděný kontejner, který přeloží manuskript z Overleafu jedním příkazem — a dokumentace, která agentovi řekne, jak ho použít. V paper repu nepřibude žádný script, devcontainer ani konfigurační soubor.

github.com/tomasvicar/overleaf_agents  ·  ghcr.io/tomasvicar/latex-overleaf:TL2025

647 MB rozbaleně 300 MB přes síť TeX Live 2025 amd64 + arm64 Linux · macOS · Windows stav: publikováno na GHCR

Princip

Overleaf běží na konkrétním releasu TeX Live — je vidět v projektu pod Menu → Settings → TeX Live version. Image se instaluje ze zamrzlého („historic") repozitáře téhož roku, takže věta „zkompilovalo se to lokálně" něco vypovídá o tom, jestli to projde i na Overleafu.

Tahle parita je důvod, proč se neřeší kompilace přímo na Overleafu. Overleaf nemá veřejné compile API; cesty přes neoficiální endpoint nebo headless browser jsou křehké a šly by přidat později, ale pro to, co potřebuješ, nejsou nutné.

Image je záměrně malý: scheme-basic plus kurátorovaný seznam balíčků. To je jediné místo, kde se od Overleafu liší — ten jede TeX Live full.

Proto se všude v repu píše rokový tag :TL2025, ne :latest. :latest se posune na nový ročník ve chvíli, kdy se posune tenhle repo — což je přesně to, co pinning nemá dělat. Publikované jsou dva tagy, TL2025 a latest, a dneska ukazují na tentýž image; příští rok už ne.

Jak se image používá

Jednou za paper

# token: Overleaf → Account Settings → Git Integration
git clone https://git:<TOKEN>@git.overleaf.com/<PROJECT_ID> <my-paper>
cd <my-paper>
git remote rename origin overleaf

# GitHub je volitelný — Overleaf sám o sobě je platný setup
gh repo create <repo> --private --source=. --push

Git bridge je placená funkce vázaná na vlastníka projektu, ne na tebe: projekt, který ti nasdílí kolega s předplatným, jde naklonovat i z free účtu. Nefunguje jen vlastní projekt na free účtu — tam žádný remote není. Token skončí v čitelné podobě v <my-paper>/.git/config, nikde jinde; do repa se nedostane a na Overleaf se nesynchronizuje.

Pak už jen tohle

git pull overleaf main --no-rebase
docker run --rm -v "$PWD:/work" -u "$(id -u):$(id -g)" \
  ghcr.io/tomasvicar/latex-overleaf:TL2025

git add -A && git commit -m "…"
git push overleaf main
git remote | grep -q '^origin$' && git push origin main

Overleaf remote se vždycky jmenuje overleaf, i když je jediný. Bez toho by se jmenoval origin v jednom setupu a overleaf v druhém a každá instrukce by musela existovat ve dvou verzích — takhle platí jedno pravidlo v obou případech, agenta nevyjímaje.

Rootless podman se chová opačně — root v kontejneru už je mapovaný na tebe, takže -u se vynechá, a na Fedoře se k mountu přidá :Z kvůli SELinuxu. Obě varianty jsem prohnal reálným během a soubory vyšly správně vlastněné.

Přes -e jde přepnout ENGINE=xelatex|lualatex, SHELL_ESCAPE=1 a OUTDIR.

Hlavní soubor se hledá ve třech krocích: argument za jménem image vyhrává, jinak main.tex, jinak jediný .tex v kořeni, který má \documentclass. Takže manuscript.tex se přeloží bez jakéhokoli argumentu; sections/*.tex do toho nevstupují, protože hledání není rekurzivní. Dva kandidáti se nehádají — kontejner je vypíše a skončí. PDF se ale jmenuje podle zdroje, takže do .gitignore patří /manuscript.pdf; všude opisovaný /main.pdf by nesedl, přeložené PDF by odteklo na Overleaf a konfliktovalo tam při každém buildu.

Windows

Původně tu stálo jen „Docker Desktop s WSL2 backendem". Ověřování na reálném Windows 11 (build 26200, WSL 2.7.11, Docker Desktop 29.6.2) to opravilo na třech místech, a všechna tři jsou teď v windows.md.

WSL2 jde první, ne Docker. Docker Desktop ho uvádí jako prerekvizitu a sám ho nezapíná — pořadí je wsl --install (administrátorská PowerShell, restart), teprve pak winget install -e --id Docker.DockerDesktop. Na Windows 11 a Windows 10 2004+ ten první příkaz zapne i potřebné Windows features. Co zapnout nemůže, je virtualizace v BIOSu/UEFI: pády 0x80370102 a 0x80070003 jsou tohle.

Použitelné shelly jsou dva, ne čtyři. Ubuntu ve WSL2 je doporučené — každý příkaz z repa funguje doslova, $(id -u) včetně. PowerShell funguje taky a potřebuje toho míň, ne víc: žádnou Ubuntu distribuci (Docker si veze vlastní docker-desktop) a žádný integration toggle. Platí se za to jen tvarem příkazu — vypustit -u a psát -v "${PWD}:/work". Výsledné PDF je bajt po bajtu stejné jako z Linuxu. Git Bash a cmd.exe podporované nejsou.

Kde soubory leží, je vidět na času. Stejný manuskript, tři čisté překlady: 11 s z filesystemu WSL2 proti 29 s z /mnt/c, tedy zhruba 2,5×. Absolutní čísla patří tomu stroji, poměr cestuje — a roste s počtem souborů, kterých se překlad dotkne, což je přesně to, co dělá bibliografie a adresář obrázků.

Zbytek jsou pasti kolem symlinků a konců řádků: Git for Windows má core.symlinks=false, takže commitnutý symlink se vyklonuje jako devítibajtový textový soubor s obsahem AGENTS.md — a agent, který ho čte, najde tohle místo instrukcí. Proto: je-li kdokoli na paperu na Windows, commitni dva opravdové soubory. Tahle past je jediná, která kousne i lidi, co na Windows nejsou.

Proč ne MCP server

Ptal ses, jestli to řešit přes skill nebo MCP server. MCP dává agentovi schopnosti, které jinak nemá — tady je ale všechno docker run a git, což agent umí přes shell. MCP server by přidal proces, závislost a konfiguraci navíc za nulový zisk.

Nosičem je proto obyčejný markdown v paper repu, pod dvěma jmény: AGENTS.md pro Codex, Gemini CLI a většinu ostatních, CLAUDE.md pro Claude Code. Symlink jednoho na druhý je udrží v souladu — ale jen tam, kde symlinky přežijí: Git for Windows commitnutý symlink vyklonuje jako textový soubor s obsahem AGENTS.md, takže s kýmkoli na Windows se commitují dva opravdové soubory. Skill je nad tím jen tenká vrstva pro pohodlí. Pravidla, která agent dostává: kompiluj v kontejneru a ne na hostu, čti první chybu z logu, chybějící .sty znamená chybějící balíček v image a ne důvod přepisovat manuskript, před pushem na Overleaf vždycky zkompiluj, nikdy neforcuj a při odmítnutém pushi git pull --no-rebase.

Dvě pasti, které testování odhalilo

Obě změnily návrh oproti tomu, co jsem původně napsal — proto stojí za zaznamenání.

tlmgr lže o úspěchu

tlmgr install vypíše install: foo [9k] a skončí s exit 0, i když se nestáhlo vůbec nic. Spolehnout se na návratový kód by znamenalo tiše vydávat rozbité image.

Proto Dockerfile po instalaci prochází packages.txt položku po položce přes tlmgr info --only-installed a vypíše všechna vadná jména najednou. A proto je v dokumentovaném rozšiřovacím Dockerfilu && kpsewhich — je to jediné, co z tichého selhání udělá selhaný build.

runtime stage neměl čím stahovat

V runtime vrstvě chyběl curl i wget — byly jen v installer stage. tlmgr tak neměl jak stáhnout balíček a v kombinaci s pastí výše to vypadalo jako zablokovaná síť. Doplněný curl a ca-certificates to řeší.

Kvůli tomu jsem taky vyhodil původně dokumentovaný tlmgr --usermode do persistentního volume — do namountovaného stromu nezapisoval. Nahradil ho dvouřádkový Dockerfile nad publikovaným image, který používá systémový strom a je cachovatelný.

Co zbývá tobě

  1. Nakopírovat AGENTS.snippet.md do paper repa jako AGENTS.md a CLAUDE.md (symlink stačí, pokud nikdo na paperu nejede na Windows) a přidat build/, aux přípony a jméno přeloženého PDF do .gitignore. Tím je paper repo hotový — nic dalšího do něj nepřibude. Tohle je přesně ten krok, který podle README udělá agent, když ho v naklonovaném adresáři pustíš na tenhle repo.
  2. Zkontrolovat TeX Live rok v Overleaf projektu a srovnat ho s image. Když se rozejdou, parita — na které celý návrh stojí — přestane platit. Mění se na třech místech: DEFAULT_TL_YEAR a matrix ve workflow, TL_YEAR v Dockerfilu.
  3. Počítat s tím, že paper_adherence s biophys-new.cls nejspíš na první pokus vyžádá nějaký balíček navíc do packages.txt.
Zamrzlé („historic") repozitáře TeX Live jsou důvod, proč rokové tagy budou fungovat i za rok: :TL2025 se instaluje z archivu, který se už nemění. Starší ročníky publikované nejsou — docker build --build-arg TL_YEAR=2024 . si je postaví z téhož archivu, ale CI tu cestu netestuje.
